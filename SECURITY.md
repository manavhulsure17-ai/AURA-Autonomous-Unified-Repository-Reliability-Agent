# AURA Security Architecture & Threat Model

AURA is engineered with defense-in-depth principles to prevent prompt injection, unauthorized code execution, secret exposure, and accidental production degradation.

---

## 1. Threat Modeling & Mitigations

| Threat Vector | Potential Impact | AURA Defense Mechanism |
|---|---|---|
| **Prompt Injection in Code Comments** | Agent hijacked into generating malicious payloads | Strict AST parser strips comments before prompt synthesis; Semgrep AST taint rules validate all outputs. |
| **Sandbox Escape** | Container compromised to access host infrastructure | Ephemeral Docker containers run without `--privileged`, with dropped Linux capabilities (`CAP_DROP=ALL`), read-only root filesystems, and strict CPU/memory cgroups. |
| **Secret Exfiltration** | API keys or credentials leaked into LLM prompts | Automated client-side and server-side regex + entropy scanner redacts high-entropy tokens (`AKIA*`, `AIza*`, `sk_live_*`) before LLM ingestion. |
| **Destructive Rollouts** | Erroneous AI hotfix applied to production | Mandatory Human Approval Safety Gate blocks all deployments with high blast radius until explicit operator confirmation. |
| **Tampered Audit Trails** | Malicious actor modifies historical logs | Every event and proposal is signed with an Ed25519 cryptographic key and chained into an append-only ledger. |

## 3. Human Approval Safety Gates

AURA enforces an explicit human-in-the-loop requirement for:
1. **Pull Request Merging**: Merging any patch generated by `RefactoringAgent` into primary branches.
2. **Production Hotfixes**: Applying self-healing config mutations to Kubernetes cluster deployments.
3. **Database Schema Migrations**: Any modification to table columns, indexes, or raw data structures.
